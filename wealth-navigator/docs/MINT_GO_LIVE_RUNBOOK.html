Mint OEMS — Production Go-Live Runbook

Get IRESS data flowing into Supabase via a single Railway worker, then have every website read Supabase — and get a live second-by-second fan-out to 2–3 sites for free.

Source of truth: wealth-navigator/docs/GO_LIVE_RUNBOOK.md. This document distils the runbook for in-browser use; the markdown file remains authoritative.

1. Executive summary

Goal. IRESS market data lands in Supabase Postgres on every tick. Vercel-hosted sites (and any future sister site) read quotes from Supabase and subscribe to Supabase Realtime for second-by-second updates. The Railway worker is the single IRESS license holder; the UI tiers never speak to IRESS for the hot read path.

Binding constraint. Our DFM@Mint entitlement is a single concurrent IRESS session. Every architectural decision below flows from that fact.

Three platforms, distinct jobs.

V

Vercel — Next.js UI, BFF routes, SSE pipes to browsers. No IRESS for live data.

S

Supabase — Postgres (source of truth), Auth, Realtime broadcasts.

R

Railway — long-running IRESS worker, sticky ApplicationID, single replica.

I

IRESS — CT (testing) for staging, prod only after Charles approves. License seat = 1.

Mental model in one sentence

Worker writes rows; Supabase shouts rows; every site hears the shout. Sites never speak to IRESS for live data — they only ever listen.

2. Architecture

Three platforms, one database, one license. The Railway worker is the only thing that touches IRESS in production. Sites only read from Supabase.

3. The single-license reality

DFM@Mint appears to be 1 concurrent IRESS session.

Every design decision in this runbook exists to keep that single seat in the right hands. If we ever get a second seat, Phase 4 of the runbook is where we re-architect — not before.

25008 is never a bad password. It means "No more licenses available" — another process already holds the seat. The fix is to stop the other process, not to rotate credentials.

Non-negotiable rules

1

Only one process ever holds the license. The Railway worker is that process. Period.

2

Vercel functions do NOT call IRESS for live data in production. IRESS on the UI tier is for admin / one-off actions only (e.g. a manual PricingQuoteGet from a debug route).

3

Railway worker = single replica only. Scale-out is off the table until Charles gives us 2+ seats and we add license pooling.

4

All sites read Supabase, never IRESS. That includes the OEMS dashboard, the strategist console, and any future sister site.

If Charles gives us 2+ licenses later

Document before splitting. Reasonable split:

  • Seat 1: Railway worker — long-poll quote sync (hot path).
  • Seat 2: admin / one-off actions (order placement, manual lookups) — could run on Railway admin service or a dev worker.
  • Seat 3+: only after we've audited concurrent patterns and proven no contention.

Until that day, run with one seat and assume the next 25008 is yours to debug.

4. Live data fan-out strategy

The question the team keeps asking: how do we push live data to 2–3 sites that update every second?

Path A — Supabase Realtime (recommended)

Worker writes to stock_intraday_c. Supabase broadcasts every row change to all Realtime subscribers. Each site subscribes via the standard Supabase JS client.

// In the BFF or a long-lived client component
const channel = supabase
  .channel('quotes')
  .on(
    'postgres_changes',
    { event: 'INSERT', schema: 'public', table: 'stock_intraday_c' },
    (payload) => {
      // push to SSE on /api/ticks; heatmap/blotter/cards re-render
      onTick(payload.new);
    }
  )
  .subscribe();

Why this is enough. Supabase Realtime is a managed fan-out. We get WebSockets, presence, and broadcast channels without running our own server. Vercel functions can subscribe on demand; browsers can subscribe directly from the client SDK.

Path B — Add Upstash Redis (optional upgrade)

If Postgres changes feel like the wrong tool (e.g. we need pure pub/sub with no row history), add Upstash Redis pub/sub on top: the worker still upserts Postgres (source of truth) but also PUBLISHes a JSON tick to a Redis channel. Sites subscribe to Redis instead of Postgres changes.

Use Path B only if Path A's throughput becomes a problem. Postgres changes are not the bottleneck for 10–50 watchlist symbols at one tick per 15s.

What we explicitly do NOT do

X

WebSocket from the worker. Vercel can subscribe; we don't need a custom WebSocket server. Don't build one.

X

Poll IRESS from each site. That's how you get license fights, slow responses, and inconsistent snapshots across tabs. Read the row instead.

X

Long-poll IRESS from Vercel functions. Same reason. The license is the worker's, not the function's.

Why 2–3 sites get this for free

Every site is a subscriber to the same Supabase channel. They never compete for the IRESS seat. Adding site #4 means a new Vercel project and a new supabase.channel('quotes') subscription — zero extra IRESS load.

PHASE 4

Wire UI to Supabase (live fan-out)

Goal: flip the UI's read path from IRESS to Supabase and add the Realtime subscription so 2–3 sites get live ticks in lockstep.

  1. Flip USE_SUPABASE_QUOTES=1 in Vercel production env.

6. Live data flow — second-by-second

What happens between an IRESS tick and a re-rendered heatmap tile. Latency budget assumes a healthy Supabase region and a single in-flight update per symbol.

T+0ms IRESS PricingQuoteGet (every ~15s per symbol) T+50ms worker upserts stock_intraday_c (cents) T+80ms Supabase Realtime broadcasts row to all subscribers T+100ms each Vercel site pushes SSE to its connected browsers T+150ms heatmap / blotter / balance card re-renders

Under load, the slowest segment is usually the worker's SOAP round-trip; Postgres writes are sub-10ms; Realtime fan-out is typically < 50ms within a region. Two-region Vercel deployments add cross-region latency, mitigated by the /api/quotes REST endpoint as a fallback.

7. Multi-site replication (the 2–3 sites question)

Adding a second or third site to the same data feed is straightforward because sites are subscribers, not producers.

What each site needs

  • Its own Vercel/Next.js project (or a shared project on the same domain).
  • Its own NEXT_PUBLIC_SUPABASE_URL + NEXT_PUBLIC_SUPABASE_ANON_KEY.
  • Its own SUPABASE_SERVICE_ROLE_KEY (server-only, for the BFF).
  • Its own USE_SUPABASE_QUOTES=1.

What each site does NOT need

  • IRESS credentials (only if it does direct calls — recommended: no).
  • Its own Railway worker — one worker feeds all sites.
  • Its own Supabase project — share the same one.

Drift control

Every site reads the same Postgres row. There is no per-site state to drift. As long as each site subscribes to the same Supabase channel and reads the same table/view, two browser tabs on different sites show the same price within Realtime's fan-out window (~50–100 ms within a region, a touch more cross-region).

Adding a new site is a Vercel-only exercise

New project → copy env → deploy. No IRESS involvement, no new worker, no new Supabase project. The architecture is "many listeners, one source of truth, one license holder."

10. Glossary

TermMeaning
ApplicationIDIRESS-side identifier for the calling process. The worker uses a stable IRESS_APPLICATION_LABEL + hostname/GUID so restarts reuse the same session where possible.
IRESSSessionKeyThe opaque token returned by IRESSSessionStart that the worker uses on every subsequent SOAP call.
ServiceSessionServer-only long-running session that the Railway worker holds. Distinct from a per-request UI session.
25001IRESS SOAP fault: invalid session. The auto-recover path in WorkerSessionManager rebuilds the session and retries.
25008IRESS SOAP fault: no more licenses available. Means another process holds the seat — not a bad password.
NoUpdateBlockTimeIRESS server-side coalescing window for repeated quote calls with no change. The worker respects it implicitly by polling at a steady interval.
RLSRow-Level Security. Postgres feature that gates rows by role. We use SELECT-only policies for anon/authenticated on intraday tables; writes are service_role only.
RealtimeSupabase-managed pub/sub over Postgres changes. The fan-out channel for live ticks.
Sticky sessionAn IRESS session bound to a stable ApplicationID and ServiceSession so restarts don't churn sessions and licenses.
